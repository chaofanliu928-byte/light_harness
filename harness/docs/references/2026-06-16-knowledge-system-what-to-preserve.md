## A. 该保留什么 —— 一条判据

> **存那些"就算读全代码也要花大力气重建、或根本重建不出来"的层。代码本身留给代码当唯一真相(SSoT),但它上面那层抽象要文档化、先写、保鲜。**

| 该存 | 为什么(代码答不出) | 别存什么(会腐) |
|---|---|---|
| **为什么**(决策 + 否决的备选) | 代码只有 What 没有 Why | — |
| **要解决的真问题**(意图/spec) | 代码是解法不是问题 | — |
| **守住什么**(不变量/约束) | 代码不会喊"这条线别碰" | — |
| **设计层**(架构/模块边界/接口契约/导航地图) | AI 读不全代码就漏;且要先写 | 逐字复述代码的散文 |
| **踩过的坑**(教训)+ **代码残留的 why**(那个怪 guard 为什么在) | git 有 fix,没有"为什么走 B 不走 A" | 一次性 bug 事件(git 够了) |
| **你是谁**(协作偏好) | 完全不在代码里 | — |
| **当前状态**(进行到哪) | 工作记忆,短期,用完即弃 | — |

**用户两条关键修正**(已并入上表):
1. **设计层该存、且先写**——不是"读代码就行"。理由:AI 读不全代码就漏、就出错;设计层是"地图",让 agent 读对地方不漏(对齐文档第一公民)。区别 = 存**设计/契约/导航层**(抽象、变得慢),别存**逐字镜像代码的散文**(会腐)。
2. **bug 拆三层**:① bug 事件(git 够了,不另存)② bug 的教训/坑(可推广,值得存,防新地方重犯)③ bug 在代码里的残留 why(那个看着多余的 guard——留一句"因为 bug X",否则下次顺手清掉就回归;Chesterton 栅栏)。

## B. 什么时候要什么 —— 按场景(需求侧)

不按内容类型堆 wiki,按"AI 在某场景伸手拿什么"组织。

| 场景 | 这一刻要什么 | harness 现状 |
|---|---|---|
| 会话开场/接手 | 进行到哪 + 欠账没 + 读哪些书 | ✅ handoff + 对账 |
| 第 0 步定位(陌生 repo) | 这是什么 + 先读什么 + 硬规矩在哪 | ✅ AGENTS.md |
| 理解意图/需求 | 真问题 + 约束 + 你的偏好 | ⚠️ 意图散在 spec |
| 方案/设计 | 架构怎么分 + 契约 + 类似决策 + 不变量 + 调研 | ⚠️ 料在,没按"设计这块时自动喂"组织 |
| **写代码** | 这块契约 + 模块边界 + "这段为什么怪" + 本任务 spec | ⚠️ **缺口** |
| 审查 | 判据 + 不变量 + spec 原意 + 坑清单 | ✅ review-rules + 守 Y |
| **调试/排错** | 踩过的坑 + 已知问题 + code why | ⚠️ **缺口** |
| 收口 | 收口工序 + 凭证义务 + 台账更新 | ✅ finishing/credentials |
| 要做决策时 | 以前定过没 + 你拍板没 + 原则 | ✅ decisions/decision-trail |
| **要清理/重构某段** | 这段为什么在 + 碰了破不破不变量 | ⚠️ 靠注释,不系统 |

## C. 三者边界(知识 / 偏好 / 规则)

| | 规则(干活规矩) | 偏好(用户偏好) | 知识(决策/调研/真相) |
|---|---|---|---|
| 性质 | 命令式、普适、有执法 | 你特定的协作风格 | 描述式、当背景、不强制 |
| 住址 | `docs/governance/` | `docs/preferences.md` | `decisions/` `references/` ARCHITECTURE |
| 要凭证 | 要 | 也要(D11) | 不要 |

**糊的地方(没定论)**:偏好会硬化成规则(做审分离从推理变铁律)/ 决策会隐含规则 / memory 把三者拍平成四型、书架却分格——这层镜像边界不清。

---

## D. 两镜头合起来 → 三个洞

1. **大部分场景只要一小块,不要全知识** → 正确形态是"按场景索引 + 按需拉",不是大 wiki 全塞窗。这也回答"格式":格式应让 AI 在某场景快速拿到那一块。
2. **harness 做得好的(✅)有共同点:进这个场景就自动读对应的东西**(开场读台账、审查读 review-rules…)——它的脊柱 = 知识挂在它服务的场景上。
3. **缺口(⚠️)集中在:写代码 / 重构 / 调试**——设计层的契约 + 地图 + "为什么这段在" + 坑,料都存着,但没按"哪个场景需要我"送到手边 → AI 只能读全代码(漏)或清掉不懂的 guard(回归)。正是用户最早戳的"读不全就出问题"。

---

## E. 候选子项 + 决定的执行排序

| 候选 | 解决哪个缺口 |
|---|---|
| **★ 设计层到手边**(契约/模块地图/why/坑,在写代码·重构·调试场景可靠拉到) | ⚠️ 三个缺口一锅端 |
| **反腐烂/新鲜度**(freshness 元数据 + 软提醒) | 已存的会腐 |
| **边界厘清**(知识/偏好/规则) | C 的糊地带 |

**决定的排序(2026-06-16,用户拍板「按你的顺序执行」)**:

0. **落本梳理草稿**(本文件)——便宜、覆盖面大、当锚,先文档后动手。
1. **反腐烂/新鲜度** 先——理由:① 最小最快(照 check-context-chain 范式)② 立刻护住已有知识(它真在腐:5 天前的地图已部分过时)③ **是 ★ 的地基**:设计层地图一旦旧了会误导实现者,比没有还糟,故先保鲜再堆内容。
2. **★ 设计层到手边**——最痛最密的缺口,但最大、最需 brainstorm 收敛"怎么挂/怎么触发";要 1 的保鲜 + 0 的判据就位。
3. **边界厘清** 随——不单独前置(纯概念易空谈);等 ★ 往书架加新层时拿真案例解(对齐「边做边提升」)。

> 替代方案(未选):把"设计层保鲜"并进 ★ 一起做,全局反腐烂留后。选「分开」是为快赢 + 立刻给全部已有知识止损 + 节奏稳。

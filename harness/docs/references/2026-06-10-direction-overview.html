0一页总览

整条故事线,五句话。

  1. 方向主张(用户):随模型变强减脚手架——ultracode 已能实现部分脚手架功能,但更凸显逻辑和流程的重要性。
  2. 内部证据:60 个脚手架组件逐项对照,无一被 ultracode 完全覆盖;可让渡的是"扇出/并行/格式强制"等执行机器,留下的承重墙是流程知识、触发保障、跨会话状态、下游分发。
  3. 外部证据:Anthropic 实测拆掉 context resets 和 sprint 分块(执行结构),留下 planner 和 evaluator(判断角色);OpenAI 把文档治理做得更机械化而非更少——业界与主张同向。
  4. 因此重心移到三件事(用户判断,证据支持):怎么定义任务(出生即带验收标准)、怎么调度工作流/loops、怎么验证任务——三者连成闭环,载体是知识组织(llm-wiki 方向)。
  5. 当前最大缺口:handoff 与上下文库割裂、调研产物入库不挂链、"每一步参考哪些上下文"散在三种机制里没有统一形态——闭环机制是下一个 feature,入口是 brainstorming 需求对接。

1方向主张与证据结构

主张是用户提出的;下面是它两侧的证据(内部 + 外部),以及一个最关键的概念区分。

✂️ 可让渡:执行机器

  • 并行 fork N 个隔离挑战者的扇出指令
  • "材料完整嵌入 prompt"类旧运行时补丁
  • "格式不符重试一次"的人工结构强制
  • 单 turn 并行约束(防串行下发的补丁)

ultracode 的确定性脚本编排原生覆盖且更可靠。仓库已有让渡样本:research-scout 把执行交给 deep-research,只留判断层。

🧱 承重墙:逻辑与流程(四类 + 一)

  • 流程知识:审什么维度/什么算 critical/评分标尺/回退表
  • 触发保障:hook 事件必跑 + 阻断 vs 运行时逐回合 opt-in
  • 跨会话状态:handoff/audit 台账/分数趋势/决策留痕
  • 下游分发:不开 ultracode 的环境也要拿到约束
  • 防绕过条款:约束对象恰是即兴编排者自身,即兴在结构上不可能自带"约束即兴"的东西
一处方向性冲突,做让渡时必须显式带上:ultracode 原生的"多数票裁决"恰是 synthesis-rules 事后规则 3 明文禁止的从众判法("多数挑战者都说 X → 默认 X 对"不允许)。删治理只留运行时,部分默认机器行为与现有治理标准相反。

3业界时间线:脚手架观的演变

一手文章经 3 票对抗核验。横切观察:被拆的均为执行结构,存留/加强的是判断角色与文档治理。详见 文献地图一。

2024-12

Anthropic《Building effective agents》:简单可组合优先,可论证改善时才加复杂度(理由=可调试性);命名 evaluator-optimizer 模式。

2025-06

Cognition《Don't Build Multi-Agents》:反对多 agent(写入冲突);Anthropic 多 agent research 系统:成本 4×/15× token。

2025-09

Anthropic:"smarter models require less prescriptive engineering"——时间性论证首次出现;agent loop = 收集上下文→行动→验证→重复。

2025-11

Anthropic:"compaction isn't sufficient"——只给高层 prompt,Opus 4.5 也造不出生产级应用,harness 结构必要(注意时点限定)。

2026-02

OpenAI《Harness engineering》:约 100 行 AGENTS.md 当地图、docs/ 当 system of record、linter/CI/doc-gardening agent 机械化治理文档腐烂——文档治理更机械化而非更少。

2026-03

Anthropic 实测拆脚手架:context resets 因 Opus 4.5 移除、sprint 分块因 Opus 4.6 移除;planner/evaluator 保留("Without the planner, the generator under-scoped");方法论:"when a new model lands…re-examine a harness, stripping away pieces that are no longer load-bearing";结论:"the space of interesting harness combinations doesn't shrink…Instead, it moves"。

2026-04

Anthropic《Managed Agents》:"Harnesses encode assumptions that go stale as models improve"(context anxiety→resets→dead weight 实例);Cognition 立场收窄:写入单线程的多 agent 可行,审查 agent 与编码 agent 不共享上下文效果最好(每 PR 抓 2 bug、58% 严重)——反方阵营给"做与判分开"的独立佐证。

转引警告:三条流行说法被 0-3 否决——"多 agent 比单 agent 高 90.2%"、"context rot"那套表述、"orchestrator-workers 模式定义";Zep 论文 DMR 对比数字同样被否。引用前回源。

6三件事与闭环(用户判断 + 证据映射)

用户判断:现在重要的是 ①怎么定义任务 ②怎么调度工作流/loops ③怎么验证任务;且 agent 智力足够,缺的是上下文、规范流程、每步参考什么。

用户判断业界证据落点
定义任务(模糊理念→确定问题)Anthropic 留 planner:"Without the planner, the generator under-scoped"
调度 workflow/loopsagent loop 官方骨架(收集→行动→验证→重复);拆掉的是 sprint 分块,留下编排逻辑
验证任务留 evaluator("worth the cost when the task sits beyond what the current model does reliably solo");Cognition:审查不共享上下文最好
智力足够,缺上下文与流程"compaction isn't sufficient…if it's only given a high-level prompt"(能力不是瓶颈);"anything it can't access in-context…effectively doesn't exist"(OpenAI);限定:evaluator 边界仍在,验证环节不能省
收紧:定义和验证是同一件事的两端。验证标准应该在任务定义时产出("怎么算完成"是需求清单的一部分)——evaluator-optimizer 的适用条件原话就是"有清晰评估标准",标准从定义来。

闭环(通用机制的形态——一半零件已存在)

任务定义契约含出生时的验收标准
→
每阶段上下文清单这一步读什么/写什么/怎么算完成
→
执行运行时机器(扇出/loops)
→
验证按出生时的标准验
→

已有零件:治理表(阶段→规则)、session-init(起点注入)、L1-L6(知识挂链)、RUBRIC + Evidence Depth(验证标尺)、brainstorming 必产需求清单。缺的接线:"每一步读什么"散在三处(治理表靠拉/session-init 硬编码推/skill 注入)没有统一机读形态;验证结果不回灌;调研产物不挂链。业界形态参照:plans-as-first-class(OpenAI)+ 渐进披露三级(Skills)+ schema 层(Karpathy)。

7任务的出生:怎么带着上下文和行业认知出生

用户追问:任务出生带验收标准 → 出生就需要上下文和行业认知,怎么做到?答案:把"出生"做成一个有供给清单的流程节点,三路输入在需求对接时汇聚。

路 1:项目上下文(推 + 拉)

  • 推(已有):session-init 在会话起点注入 handoff/最新评估/活跃设计——任务出生时的"现状包"
  • 拉(已有但散):brainstorming 深挖探查 + 知识库 agentic search(文件组织好,agent 自己 grep——Boris Cherny 路线)
  • 缺:出生节点的机读清单("定义任务必读:L1 vision、L2 index、相关模块 README、相关 decisions")

路 2:行业认知(调研作为出生的标准环节)

  • 已有:research-scout 触发判据(可逆性×熟悉度)定义在 brainstorming 阶段四;deep-research 执行——本周三份文献地图就是手动跑了一遍这个环节
  • 缺两个契约:① 调研产物落库必须挂链(否则下个会话找不到——今天的现行实例);② 需求清单的验收标准字段必须引用调研结论作依据(行业认知不是读完就完,要变成验收条款,如"反腐烂机制对齐 freshness+owner 模式")

路 3:标尺库(验收标准的词汇表)

  • 验收标准不是每次凭空写 = 任务专属条件 + 可复用标尺引用(RUBRIC 维度、Evidence Depth 档位、治理标准)
  • 业界最小实现样本:Anthropic initializer agent 把产品 spec 分解成 JSON feature 清单——每个 feature 出生就是可勾选的

汇聚与角色边界

AI 结合三路输入起草需求清单 + 验收标准 → 人确认(对应现有硬规则"需求清单必须用户确认"+"AI 列选项人拍板")。

结论:不需要发明新东西,需要把三路输入在出生节点契约化——出生清单(读什么)、调研挂链(行业认知怎么进来并留下)、标尺引用(验收标准怎么落字段)。

8割裂诊断:handoff × 上下文库

用户观察"handoff 和上下文库有点割裂,没有很好使用"——已对到仓库实际状态,确认成立,三条现行证据(2026-06-10 实测)。

  1. handoff 停在 2026-06-05,本周 5 个 commit(三份文献地图+模块地图+本页)它全不知道,"下一步"里没有本周任何一条线。
  2. handoff(状态快照,80 行模板)与上下文库(知识结构)之间只有一根线:收口时的 context-chain: 已核/skipped 声明字段——是检查点不是信息链,且自仓库还是 skipped。
  3. 三份文献地图进了 references/ 但没有任何入口指向它们(references/README 未列、handoff 未提)——知识入了库,没有线接到下一个会话的起点。(README 索引已于本页生成同日补上,机制性缺口仍待设计)

结构原因:handoff 与活上下文链是不同时期为不同目的设计的(会话连续 vs 知识分层),session-init 推送的内容(handoff/评估/设计头)与靠"拉"的知识区(references/decisions)是两套供给方式,没有统一机制——这正是第 6 节"每阶段上下文清单"要解决的。

## 0. 核心 reframe:不是三个盒子,是两轴 + 一条流

§C 的"三格表"会误导成"三类并排、各归各位"。真相:

- **memory 按"出处"分**(关于谁 / 来自哪):user / feedback / project / reference。
- **书架按"性质·执法力"分**:规则 / 偏好 / 知识。
- **两轴正交** → 同一型 memory 横跨多个书架格。最硬证据:`memory.feedback` 一型,有的已硬化进 governance 当铁律(→规则格)、有的落 preferences.md 当协作风格(→偏好格);同一型,落点不同。
- **边界是流动的**:偏好 / 知识会**往规则那头硬化**(获得普适 + 执法时),不是静态归属。

---

## 1. 决策程序(真案例照此判)

**Q1 — SCOPE(跟谁走)**:
- 关于用户本人、跨项目复用、跟人走 → **memory**(私域,四型按出处)。
- 关于这份活、绑本项目、要凭证/分发/执法 → **书架**(仓内权威)。
- **偏好 = 合法重叠**:同一条用户偏好两处都有,靠"权威 vs 缓存"不是二选一 —— preferences.md = 仓内 SSoT,memory = 跨项目缓存镜像,冲突以仓内为准(D11 已是范本)。

**Q2 — 书架内按"要不要执法"选格**:
- 不强制、描述式、当背景 → **知识**(decisions/ references/ ARCHITECTURE,不要凭证)。
- 这个用户的协作风格 → **偏好**(preferences.md,D11 忠实性凭证)。
- 强制 + 普适 + 有执法 → **规则**(governance/,audit 凭证)。

## 2. 三条"升格"判据(边界流动的方向 — 都从真案例反推)

### 2.1 偏好 → 规则:两闸都过才升

- **①普适性闸**:对所有走 harness 的项目都成立(不只某次对话的临时纠正)。判据 = 能否表述成与具体项目无关的命令。
- **②执法点闸**:存在能拒绝违反的落点(三种,见 §3 连续谱)。
- 两闸都过 → 升 governance 规则;只过普适 → 留 memory/decision 当背景知识;只过执法不普适 → 项目局部约定不外推。
- **范例(精确瞬间)**:做审分离最初是用户哲学(memory `feedback_design_philosophy`)。2026-05-13 meta-review 应修 #8 补上「任何主张同 agent 既做又审,违反公设1,**默认拒绝、不进入辩论**」—— 这一句把"可辩论的偏好"变成"默认拒绝的规则",**就是硬化的精确瞬间**。(证据:`audits/meta-review-2026-05-13-165053-twin-axioms-and-synthesis-rules.md` + `CLAUDE.md` 反向规则 + `decisions/2026-04-16-fork-flat-refactor.md`「不是项目特例,是结构性问题」。)
- **干净范例**:`design-rules.md`「反模式约束(用户 feedback 硬编码)」段 = 4 条 memory feedback 升成设计阶段强制规则,每条括号反指 `feedback_X.md`。

### 2.2 决策 → 规则:`形式可判 × 漏改损害大`,不然停在 decision record

- 决策约束未来是**常态**,**不是** extract 成规则的理由。
- **判据一(形式可判性)**:hook 可判(glob/grep/协议比对)→ 可升机器执法;只能审查/人判但有稳定形式 → 升人执行收口规程;纯判断无形式判据 → 不能 extract,只能当知识/原则反复被人调用。
- **判据二(漏改损害)**:损害大且跨会话 → 值得 extract;暴露面≈0 → 不做,留 decision record 当历史快照(YAGNI)。
- **两条任一不满足 → 停在 decision record(知识);都满足 → 升 governance(规则),升多高看形式强度。**
- **第三态(批内审验吸收)**:一次性、当批可审验完的约束(如 drift-scout「零改」)—— 既不进 governance 也不立 decision,只留一行痕,靠当批 audit 消化。
- 范例:preferences glob 行(升机器执法)/ decision-trail append(升收口规程,明拒机器 hook,预登升级触发器)/ D1 sentinel 协议(升)vs D2/D3/D6(暴露面≈0 不升)/ iterative-progression(纯判断,留 memory + decision-trail 当否决依据)。

### 2.3 memory.feedback → 规则:成熟度函数

- **未验证 = 偏好**(默认落 preferences.md,保"跟人走、判断权在用户、原话留痕")。
- **反复验证适用 = 规则**(走显式升格管道硬编码进 governance 当反模式约束;原偏好条目标注"已升格→指向规范位置")。

## 3. 执法是连续谱,不是"有/无"二分(§C 表的修正)

§C 表写"规则有执法、知识不强制"。实证否定这个硬边界 —— 执法强度是一条谱(硬→软):

1. **机器 hook + 对账**(glob 可判:preferences.md / governance/*.md 命中 credentials.conf → check-audit-coverage 对账要 audit)。
2. **审查维度**(对抗审查据此扣分:design-review 4 维含反模式约束)。
3. **结构强制 +「默认拒绝/不进入辩论」**(无法 glob 化的约束的唯一形态:做审分离的角色分离表 + 二公设反向规则)。

→ "规则 = 有执法"成立,但"有执法"本身分三档强度;书架三格的"有/无执法"二分在第 3 档(规范性执法)处是连续谱。

## 4. 搬家后的纪律:拆,不要拷(防 double-write 腐)

- 命令式(必须 / 默认拒绝 + 执法点)住 governance/CLAUDE.md;why/origin/用户原话住 memory `feedback_*` 或 decision 文件。
- 用**引用不拷贝**连:governance 条目后括号反指 `feedback_X.md` / decision 路径(`design-rules.md` 反模式段是干净范例)。
- **double-write 信号**:同一段用户原话的解释性散文同时出现在 governance 正文 + memory 正文 → 把 governance 侧压成单行命令 + 反指。

## 5. 真正没定论的地方(诚实 — 边界真渗血处,留给真案例)

1. **规范性执法(默认拒绝)无机器可核** —— 做审分离全靠调度者 LLM 自觉,没 hook / 对账能验"这次有没有同 agent 既做又审"(process-audit 抽查是事后、非每批)。名义"有执法的规则",**实际强度介于偏好与规则之间**。
2. **硬化判据从没成文** —— repo 没一处写明"偏好满足什么条件升 governance";二公设升格是 meta-review 临场补的、反模式段是手工硬编的,**全事后追认**。本留痕的 §2.1 两闸是反推隐律 —— **本留痕把它写下来了,但仍是"料"不是"规则",不据此执法**。
3. **第三态(批内审验吸收)无制度名分** —— 没判据说"什么约束算一次性可吸收 vs 需沉淀给未来批";"经审验"是事后追认不是事前判据。
4. **"判 0 不做"是乐观偏差高发区(公设1 自适用),且无兜底** —— "暴露面≈0 所以不 extract"靠当时估计,**没任何机制事后复核**这些判断是否真没出险。这是"决策→是否成规则"链上**唯一无对抗审查兜底**的环节,也是四缺口里**唯一有牙齿、可机制化**的候选(若将来啃:收口对"判暴露面≈0 不做"的决策做一次对抗抽查 —— 那要 brainstorming,独立子项)。

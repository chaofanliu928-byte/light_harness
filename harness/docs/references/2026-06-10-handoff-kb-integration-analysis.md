## 一、四个先于方案选择的地基事实(对抗审查烧穿到了地基之下)

三案的反驳者独立会师在同一批事实上。它们不是任何方案的缺陷,是**现状的事实**,且改写了之前的割裂诊断:

### 事实 1:自仓库的 hook 执法层实际不在场 ✓

- hooks 只注册在 `harness/.claude/settings.json`,命令路径 `$CLAUDE_PROJECT_DIR/.claude/hooks/*` — 只有从 harness/ 子目录启动会话才加载。
- 实际会话从仓库根启动(本周全部会话即是;根 settings.local.json 数十条权限累积证明这是长期常态)。✓ 抽查:根 `.claude/` 只有 settings.local.json(纯 permissions),无 settings.json、无 hooks。
- 即便加载,session-init / check-handoff / check-evidence-depth 是单层路径(`$PROJECT_DIR/docs/...`),从根启动也看不到 harness/docs/(对照 check-meta-review / check-context-chain 有双层探测 — 说明问题模式已知,这三个没做)。
- ✓ 抽查:`.gitignore:3` **有意**忽略 `/.claude/`("锚定 root") — 根级接线即使建了也进不了版本库。
- **归因改写**:C6-①(handoff 停更 5 天、7 commit 穿过)之前被归因为"纪律失效"——错。check-handoff 的 10 分钟新鲜度闸**从未运行过**。机器缺位,不是纪律失灵。同理,session-init 的"推送"在日常会话里也是零——本周所有会话都没有被注入过 handoff。

### 事实 2:执法时点与问题发生时点错位

- C6 三条实证全部产生于**不走 finishing 的调研/留痕直提交**(git 实测:80c018e 后 7 commit 中 5 个是纯留痕,无任何收口流程伴随;399f356 的索引是事后手动补的)。
- 纯留痕文件不命中任何 scope glob → scope=none → 不进任何治理流程;调研会话无开发分支 → finishing-a-development-branch 不触发。
- 而三案的新执法点(入边核/晋升检查/索引登记)**全部挂在收口时刻** → 对实证失败场景的覆盖为零。机制覆盖的地方 ≠ 问题发生的地方。

### 事实 3:handoff 契约的真实同步面是 4 处,且治理有洞 ✓

- ✓ 抽查:structured-handoff SKILL.md:58 "用以下**固定结构**覆盖 docs/active/handoff.md" + :60-126 内嵌完整模板(含全部契约字段行)。**任何 handoff 字段变更 = 模板 + SKILL 内嵌副本 + hook + 分发四处同步**;漏改 SKILL,新字段在下次覆写时被静默抹掉。
- ✓ 抽查:既有漂移实证 — SKILL.md:33 用 `[待更新]` 判定初始模板,而 templates/handoff.md 全文只有 `[待填]`(0 处 `[待更新]`):**判定条件引用一个不存在的标记,双写已经在烂**。另 templates/handoff.md:61 与 SKILL:125 的 context-chain 行文本已分叉(尾注差异)。
- templates/handoff.md(契约最重的文件)不命中任何 scope glob(F 组只有 templates/*.json) — 改它永不触发 meta-review。
- setup.sh:106 对 handoff 模板是无条件 cp — 下游重跑 setup 会覆灭活交接(现存 bug,与方案无关)。

### 事实 4:跨运行时入口缺位(C1 的第 0 步没有载体)

- 仓库无 AGENTS.md(业界 6 万+ 项目的跨工具入口约定);CLAUDE.md 自动加载是 Claude Code 专属;根 CLAUDE.md(M3)甚至没有指向 handoff 的索引行。
- 换运行时/纯人工时,"先读什么"没有任何中立工件承载 — 三案声称的模型无关能力都断在发现链第 0 步。

### 另:check-context-chain 的 upstream 校验无路径分支 ✓

✓ 抽查:`check-context-chain.sh:154-155` 只豁免字面 `待定`,其余一律对编码集 grep -Fxq — **路径形态的 upstream 必然被报"断链"假警告**。这对任何想用"路径挂链"的设计都是硬约束(改 hook 或不用路径,二选一)。

## 二、三案裁决

### 方案甲(完全合并 / NOW 节点):核心被击穿,部件可回收

钢人形态:handoff 改造为知识库内唯一 snapshot 节点(NOW),frontmatter upstream 兼任"入箱边"(新留痕落库当刻挂边即有入口),lifecycle 字段显式化,蒸馏流程挂 structured-handoff,搬家批迁入链区。

**击穿点**(均有 文件:行 证据):
1. 旗舰机制(路径形态 upstream 入箱边)在下游被现有 hook 当断链**永久误报**(见事实 5),"免费校验"实为负资产;且静默违反 06-05 决定"upstream 不指路径"的硬前提,未按纪律给新事实。
2. **批 3 搬家过不了方案自设的 C5 测试**:C6 三条在批 1/2(不搬家)就已修复,搬家的功能增量为零;成本被严重低估(`docs/active/handoff` 全仓 85 处引用/32 文件,清单只列 6 处);搬完三名并存(NOW 文件/handoff-归档名/context-chain 字段名)。
3. 收口时序矛盾:蒸馏核挂在方向评估之前,structured-handoff 实际跑在评估之后 — 被检查的动作在检查时还没发生,规格逼出"拿上一批充数"。
4. "方向规则对 NOW 豁免"与"(a) 链核原文逐字保留"同稿冲突,豁免条款无处安放。
5. 上下文将满时被清单逼着"晋升" → 仓促回写污染**追加式**知识层正文,且无质量闸 — 比现状(烂 handoff 随覆写消亡)制造了更持久的新故障面。
6. 80 行预算与入箱边争地:重调研日边最先被裁,入箱机制在最需要时失效。

**可回收部件**:蒸馏判据一句话("下个功能还需要它吗?");evaluation-result 等流程信号件不属知识、不并库的剂量裁剪;"约定寄宿 owner 文件、不建无主总文档"。

### 方案乙(两家+加链):方向幸存,执法设计落空

钢人形态:零新目录、契约字段一字不动;关键决策/关键上下文两节指针化(`-> 路径` / `[未沉淀]` / `[易失]`);收口晋升检查 + 路由表 + `## 沉淀:` 声明;批 2 修 hook 双层探测与根级接线。

**击穿点**:
1. 登入口步只挂在"[未沉淀]→晋升"窄路径,C6-③ 的真实路径(调研产物直接落盘、handoff 里直接写成带指针行)不经过它 — **核心卖点对实证场景零覆盖**。
2. 格式合规无机械核:纯散文行(无指针无标记)对所有机械层不可见 — 执法仍是纪律,新增约 9 处契约面只买到"悬空指针检测"一项。
3. 自校验命令有 cwd 病(根目录跑 = 零输出 = 读作"全部通过",假阴性)+ 模板 blockquote 里的 `(-> 半角箭头)` 每次跑必出一条假断指针。
4. check-promotion 牙齿在 meta 路**永不触发**(触发条件 evaluation-result.md 在 M1 四步中从不产生)— 而自仓库改动几乎全走 meta 路。"复用 context-chain 成熟模式"复用的是一个**从未真正咬合过**的模式的外壳(其硬闸在自仓库双重门都关着)。
5. `[未沉淀]` 只有晋升/废弃二态,比活链"待定可跨收口保留+写理由"更严 — 流程规则类沉淀(要走 meta-review)在收口压力下被结构性逼向废弃。
6. 批 2 根级接线撞 `.gitignore /.claude/`(不入库、不可审、本机状态)。
7. handoff 指针按路径指 context 文件,废掉活链"改 slug 不断链"的承诺 — 割裂在新的一层重演。

**幸存内核**:指针化方向、显式欠账标记的章法、晋升路由表、"AI 核+声明+hook 逼声明"三件套形态、对 C6-① 结构根因的诊断(事实 1 最早由乙的设计师与反驳者共同钉死)。

### 方案丙(一个系统两个层 / SUPPLY):内核与乙合流,SUPPLY 本体被击穿

钢人形态:新增机读供给清单 docs/SUPPLY.md(常驻/阶段/按需三节)驱动 session-init;handoff 瘦身(状态字段+待晋升暂存+指针);晋升流程+路由表+`## 晋升:` 声明扩进 check-evidence-depth。

**击穿点**:
1. **SUPPLY 对 C6 三条的修复贡献趋近于零**:瘦身修①、晋升声明修②、索引登记修③ — 三者都不经过 SUPPLY;SUPPLY 与"session-init 数据驱动"互为存在理由(删 A 则 B 无对象,删 B 则 A 无消费者),循环论证。
2. 三键注解(head/pick/stage)装不下现有注入行为(ARCHIVED/CANCELLED 排除、降级 banner 共享变量)— 要么留清单外暗逻辑(新双写),要么行为回归已修过的 bug。
3. 治理倒退:今天改注入清单 = 改 session-init.sh = B 组必审;批 4 后同一权力 = 改 scope=none 的 SUPPLY = 零审查。每会话注入权从 scope 内搬到 scope 外。
4. "自然报警"通道被常态缺失条目(eval 归档后常态不存在、新项目 specs/plans 必空)的告警疲劳淹没;按需节(恰是对准 C6-③ 的部分)永远不经过任何执行路径,零机器信号。
5. 阶段节双标:自仓库以"M3 已管路由,再写是双写"砍掉,下游保留 — 同一论证不对称适用;且下游已有两处活的阶段路由(session-init 治理提醒、finishing-rules 行内引用),SUPPLY 是第三处。
6. 晋升牙齿同样在 meta 路死(同乙-4);精磨期 eval 文件常驻导致 hook 在义务窗口外持续点火,逼出形式声明。
7. 自己批 2 把三地图登记 SUPPLY 按需节,违反自己引用的待决 4("升常驻导航需先定 owner")。

**幸存内核**:handoff 瘦身模板(状态+暂存+指针的字段设计)、"待晋升暂存"字段名即生命周期契约、晋升路由表(与乙的合并版更全)、"工作层不长草/知识层不直插/指针向下内容向上"三铁律的表述。

### 排序分析:硬结论幸存,自身账目有错

**幸存的硬结论**:① C1(验收消费)→B(任务定义)是硬依赖,**C 先行不可行**;② 口子 D 拆两半 — 字段语义现在可定、落点等地基;③ P1/P2/P3 属性键矩阵(地基是否动 handoff 字段集/是否引入 manifest/是否链式化)是排序与地基的正确联动方式。

**被打穿处**:① D 草图的字段集与三个排序批次表内部不一致(乙案批 1 自己发明第四个字段名)— 防漂移工具自己先漂;② 契约账漏算 SKILL 内嵌模板第四同步点(见事实 3);③ "裸路径无校验器"是虚账(test -f 即教科书级可校验,与编码系统解决的改名稳定性是两件事);④ "A 先行自仓库验证最强"的探针测错位置(机制覆盖处≠问题发生处,见事实 2);⑤ 任务卡作为新工件没跑 C5 — plans/*.md 和需求确认清单已是任务级、跨会话、自动注入的现成载体。

## 三、综合后的图景(供讨论,非决定)

1. **出现了"批 -1"(地基修复)**,在任何方案、任何排序下都要做,且大半独立于方案选择:
   - hook 在场性:根级会话的执法接线(要解决 .gitignore 约束 — 选项:hooks 补双层探测 + 从 harness/ 启动会话的约定,或修订 /.claude/ 排除规则);
   - 三个单层 hook(session-init/check-handoff/check-evidence-depth)补双层探测(check-context-chain 范式现成);
   - SKILL.md `[待更新]` 死条件修复 + 模板/SKILL 既有分叉收敛;
   - templates/*.md 补进 scope(F 组 glob 一行)堵契约治理洞;
   - setup.sh handoff 覆盖 bug 修复。
2. **三案合流的幸存形态** ≈ 乙的骨架(两家保留+指针化+收口晋升)+ 丙的字段细节(瘦身模板/暂存区/路由表)+ 甲的蒸馏判据 — 但必须解决三案共同落空的两件事:**留痕落库时点的登记义务**(不能只挂收口;候选:把"落库即登索引"写成调研/留痕动作自身的步骤,如 research-scout 产出整形红线追加一条)与 **meta 路的执法触发**(不能复用 evaluation-result 条件)。
3. **跨运行时入口**(AGENTS.md 或等价物)是独立缺件,与 C1 目标直接挂钩,体量一行到一页。
4. 甲的"搬家进链区"和丙的"SUPPLY 清单"按现有证据不应进入下一阶段;若要复活,需先回答各自的击穿点。

## 四、留给用户的判断点

1. 是否认可"批 -1 地基修复先行"(其中根级执法在场性的解法需要你选:会话启动约定 vs 修 gitignore 规则 vs hooks 双层化为主)。
2. 合流形态是否作为口子 A 的设计起点(进 system-design 流程,仍会被 4 挑战者审)。
3. 留痕落库时点的登记义务挂在哪(调研动作内 vs 新的轻量触发点)。
4. 排序:在"批 -1 先行"前提下,B(任务定义)与合流 A 的先后 — 排序分析的 P1 矩阵行建议:合流形态属"P1 轻改 handoff 型",B 先行最顺;但其自仓库验证有"meta 批任务形态失真"的弱点(排序分析 weakness 2,未被反驳推翻)。

# 会话链自执法(开场对账)取代常驻守门人接线 — hook 降级为工具箱

- 日期:2026-06-11
- 状态:✅ 已决(用户拍板)
- 类型:方案选择型(三案并排)
- 取代关系:取代 spec `docs/superpowers/specs/2026-06-10-context-layer-design.md` §8.4「hook 上岗 A/B 实测分支」与 plan `docs/superpowers/plans/2026-06-11-context-layer.md` 原任务 20-23(原文见 git 历史 258b96e 版本)

## 问题

批 1 把机器闸全部建成,但"电源"没接:harness 自仓库双层结构下,从仓库根启动的会话从不加载 `harness/.claude/settings.json`(地基事实 1),hook 从未自动在场。原计划任务 20 让用户在 A 案(根级接线)/ B 案(harness/ 启动约定)间拍板;讨论中用户把问题升级为第一性重审。

## 用户原话(判断锚点)

- "session-init是不是可以通过claude.md让他这么做?同时目前模型的能力已经很强了,有一些规则遵守可以通过设计原则和子智能体的初始输入以及结果的验收来决定吧?基于这个和上面的讨论,我们重新理一遍,可以吗?"
- "不要被之前的hook影响,直接从目前的架构,设计理念,逻辑开始用第一性原理开始思考"
- (成本质询)"下一个会话开场时对账的数据来源是什么?他也会读子智能体的输入和输出吗?另外如果全读的话,会不会又造成了会话的上下文的浪费,我们有一个重点不是珍惜上下文吗?"
- "ok"(2026-06-11,对「对账=下一个会话用几行上下文,核上一个会话留的几行凭证;过程随会话死,凭证替过程说话」方案的认可)

## 三案并排

| | A 案:常驻守门人(根级接线) | B 案:启动约定 | C 案:会话链自执法(开场对账) |
|---|---|---|---|
| 形态 | 根新建 .claude/settings.json + .gitignore 改 3 行 | 约定 cd harness 启动 | 入口指令两步(读台账+对账)+ 凭证制度 + hook=工具箱 |
| 开场装载 | hook 注入 | hook 注入(记得 cd 时) | 指令驱动 Read(CLAUDE.md/AGENTS.md 每会话必在场) |
| 收口执法 | Stop hook(只见未提交 diff,执法时点错位 C6) | 同左 | 下一会话开场对账(独立上下文+天然 commit 感知) |
| 代价 | 新增 settings 双写对;F1 假点燃从理论变现实 | 纪律件;harness/ 启动会误加载 M4 分发模板当指令 | 依赖指令遵从(以模型强为前提);F1 误报在手工对账中仍会出现(不阻断) |
| 接线 | 必须 | 必须(换姿势) | 零 |

## 决定:C 案

第一性推演(2026-06-11 对话留痕):工作循环只有四个代谢时刻(开场装载→干活→验收→收口);收口是"乐观×压力"的重合点;**下一个会话是必然发生、不可绕、天然独立上下文、看得见全部已提交历史的卡点**——会话链自己当执法链,优于任何常驻守门人:

- **指令层**(CLAUDE.md/AGENTS.md)扛"知道做什么":每会话必在场、跨运行时、不怕上下文压缩;模型强则可靠——凡只靠"怕模型不听话"撑着的机制都在贬值,凡靠结构性事实(会话必死/自评乐观/内省无效)撑着的不贬值
- **编排+验收**扛"做对":批 1 全程 hook 未通电、纯软承载,批级三挑战者审查 0 Critical——实证
- **对账只读凭证不读流水**:promotion 一行文法/目录卡一行一件/audit covers 头/git log oneline;干净时增量 <10 行上下文。凭证制度本来就按"一眼可核"设计("形成结果要为下游使用专门设计内容"),对账就是那个下游
- **C6 执法时点错位被对账吸收**:对账读已提交历史,天然 commit 感知,无需任何接线(吸收非消失——窗口语义与残余见 plan 任务 20 与下方残余风险节)

## 不做(防 scope 扩散)

- **不撤** harness/.claude/settings.json 与既有 hook:从 harness/ 启动(及下游单层项目)自动触发仍是合法增强层;脚本手工模式是正身。须知:从 harness/ 启动会把 M4 分发模板当指令加载(与 B 案同款副作用),增强层使用者自担
- **不做**根级 .claude/settings.json(A 案落空;若未来要接电,先修 F1 假点燃再通)
- **不给**任务级审查结论建档(上下文经济:批级 audit+台账摘要够用;此边界已向用户交代)
- **F1 假点燃降级**:自动触发不在场;手工对账会跑到 check-handoff,误触发表现为误报(输出给 AI 读,不阻断,台账凭证合规即过硬核);加固候选留 ROADMAP,若未来接电先修
- **不改** spec 正文(immutable 取向):状态头追加一行注记指向本 decision

## 残余风险(诚实声明)

- 无痕跳过(什么都不写不归档)任何检查测不出——归档前置+git 兜底,设计已接受的边界
- 连入口文件都不加载的运行时,指令层失效——但该环境 hook 同样不存在;文件本身可考古
- 对账本身是指令,依赖下一会话遵从——多级兜底:finishing 流程也核、meta-review 也核、git 永远在;且 C 案不烧 A 案的桥(接电随时可补)
- 对账窗口是 C6 的时间窗变体:默认锚定最新 audit 的 commit time(plan 任务 20),但欠账若滑出显式天数窗且连续多会话不对账,机器不再点名——剩 finishing/meta-review/git 考古兜底(C6 被吸收改形,不是无残余地消失)
